# Specification ambiguities

This register lists each ambiguity, conflict or defect that we found in the specifications that this library
implements, and the reading that the code follows. Code comments, requirements and decisions cite its ids, for
example AMB-M2-104-12 or N-26; each id has an anchor in this file. The requirements and decisions are in
[`docs/spec/`](spec/).

The MIDI Association, USB-IF and Bluetooth SIG specifications are normative (DEC-001), and their text is not
reproduced here. Each item gives the document, the section and the page, and describes the text in our own words.
Read the specification for the exact wording. Other implementations are a secondary check, never the authority.

**Status values:** RESOLVED (the choice is recorded, and the code or the requirements follow it), DECIDE (needs a
decision), OPEN (resolved when the requirement is written), INFO (no action: an editorial error with no effect on
the code).

### Decided: zmidi-net requirement choices (DEC-NET-001, decided 2026-10-15)

The 215 zmidi-net requirements (REQ-NET-*, all planned) contain the recommended option of each item. All items decided 2026-10-15 (DEC-NET-001).

#### Behaviour on the wire

- <a id="n-01"></a>**N-01** Receive window size W for duplicate and late Sequence Numbers? Recommendation: serial arithmetic (RFC 1982) with a bit map, W a const generic, default 64 (8 bytes for each session). Confidence: 80%. Review necessary: yes, it sets the duplicate rule of every receiver. AMB-M2-124-15. REQ-NET-DATA-009. Review done: review batches a and e gave the same design and value; libnetmidi2 uses 64; FEC repeats are 2 at most, so 64 is enough.
- <a id="n-02"></a>**N-02** Late Command (inside the window, not received before): deliver or drop? Recommendation: deliver it to the caller with a late mark. Confidence: 80%. Review necessary: yes, a note can arrive out of order. AMB-M2-124-15. REQ-NET-DATA-009, REQ-NET-DATA-010. Review done: FEC repairs a gap with Commands in a later payload, so to drop them loses FEC data; libnetmidi2 delivers, Windows MIDI Services drops.
- <a id="n-03"></a>**N-03** Receive state at session start and after Session Reset? Recommendation: H = 0xFFFF with H and the W numbers before it marked, so 0x0000 is the next expected number. Confidence: 85%. Review necessary: no, 7.1 makes the sender start at 0x0000. AMB-M2-124-15, AMB-M2-124-25. REQ-NET-DATA-009, REQ-NET-RST-009.
- <a id="n-04"></a>**N-04** Does the Client repeat Invitation after Invitation Reply: Pending? Recommendation: yes, as the 6.6 note says; a Pending timeout (default 60000 ms) starts at the first Pending. Confidence: 80%. Review necessary: yes, libnetmidi2 and Windows MIDI Services stop the repeats. AMB-M2-124-10. REQ-NET-INV-009, REQ-NET-INV-027, REQ-NET-INV-028. Review done: the 6.6 note gives the reason (a lost Pending or Accepted is repaired only by a repeat); DEC-001.
- <a id="n-05"></a>**N-05** Invitation from a Client in Established Session: keep or reset the session? Recommendation: reply Accepted and keep all session state. Confidence: 80%. Review necessary: yes, it differs from the catalogue proposal of AMB-M2-124-25 (reset). AMB-M2-124-25. REQ-NET-INV-018. Review done: a late repeat of the Invitation often arrives after the first UMP Data; a reset then gives duplicate or lost data; both secondary implementations keep the state.
- <a id="n-06"></a>**N-06** What does a build without feature `auth` do with Command Codes 0x02, 0x03, 0x12, 0x13? Recommendation: the codes are always known, never NAK 0x01; Host: 0x02/0x03 from an address in Idle gets Bye 0x41, in other states NAK 0x02; Client: 0x12/0x13 get NAK 0x02. Confidence: 75%. Review necessary: yes, it sets what DEC-013 "behind the feature" means. AMB-M2-124-60. REQ-NET-AUTH-012, REQ-NET-AUTH-027, REQ-NET-CMD-002, REQ-NET-SES-004. Review done: merges batch a C-CMD-1 (NAK 0x01 after a prior Invitation) and batch c C-AUTH-01; 6.7 and 6.8 demand NAK 0x02 at the Client, so the codes must be known; Bye 0x41 in Pending Session Reset would end an active session, so it is limited to Idle.
- <a id="n-07"></a>**N-07** Sequence Number field of Retransmit Error? Recommendation: the oldest Sequence Number in the send history (Table 31), or the next number when the history is empty. Confidence: 75%. Review necessary: yes, it reverses the AMB-M2-124-02 proposal (first missing number, 7.2.3). AMB-M2-124-02. REQ-NET-RTX-006. Review done: Windows MIDI Services and libnetmidi2 both write the oldest held number.
- <a id="n-08"></a>**N-08** Retransmit Request whose first number is held but a later one is not, or whose first number is not held? Recommendation: first number held: resend up to min(end, newest); first number not held: Retransmit Error only, no resend. Confidence: 75%. Review necessary: yes, 7.2.3 and 7.2.4 conflict. AMB-M2-124-03. REQ-NET-RTX-005, REQ-NET-RTX-006. Review done: 7.2.4 forbids, with "shall not", a resend of the other held data, and that is the stronger word; Windows MIDI Services does the same.
- <a id="n-09"></a>**N-09** UMP Data received around a Session Reset that this endpoint started? Recommendation: discard in Pending Session Reset only; after the Reply apply the normal Sequence Number rules from the start state. Confidence: 70%. Review necessary: yes, it changes the batch-d draft (discard until Sequence Number 0). AMB-M2-124-14. REQ-NET-RST-006. Review done: with the draft rule a lost Sequence Number 0 with no FEC stops all data until the next reset; the new rule makes it a normal gap; both conform, because 6.11 says "may".
- <a id="n-10"></a>**N-10** Late or extra Session Reset Reply in Established Session? Recommendation: ignore a Reply that comes within the Session Reset timeout after our own reset; else start a reset (6.12). Confidence: 80%. Review necessary: yes, it limits a "should" of 6.12. AMB-M2-124-50. REQ-NET-RST-012. Review done: the literal rule gives a reset loop when a repeat crosses a Reply.
- <a id="n-11"></a>**N-11** Session Reset received while this endpoint is in Pending Session Reset? Recommendation: reply, reset, stay in Pending Session Reset until our Reply arrives. Confidence: 80%. Review necessary: no, the specification does not cover the case and the effect stays local. AMB-M2-124-49. REQ-NET-RST-008.
- <a id="n-12"></a>**N-12** Form of the FEC idle payloads? Recommendation: sender uses Figure 19 (a new Zero Length Command in each idle payload); the receiver accepts Figure 18 and Figure 19. Confidence: 75%. Review necessary: yes, it changes the Sequence Number use in idle periods. AMB-M2-124-16. REQ-NET-FEC-003, REQ-NET-DATA-004, REQ-NET-VEC-006, REQ-NET-VEC-007. Review done: Figure 19 follows the normal FEC rule with no special case; 7.2.1 gives Zero Length Commands the same Sequence Number use as other UMP Data Commands, which supports it.
- <a id="n-13"></a>**N-13** Command whose Payload Length goes past the end of the UDP payload? Recommendation: stop the read there, keep the Commands before it, send NAK 0x03. Confidence: 70%. Review necessary: yes, libnetmidi2 drops with no NAK. AMB-M2-124-21, AMB-M2-124-35. REQ-NET-PKT-014. Review done: Table 25 gives 0x03 for a Command that does not carry its necessary payload, which fits.
- <a id="n-14"></a>**N-14** UMP Data Command with pl from 65 to 255? Recommendation: accept, no NAK. Confidence: 70%. Review necessary: yes, libnetmidi2 drops it. AMB-M2-124-21. REQ-NET-DATA-001. Review done: Table 25 says that 0x03 is not for a payload that is longer than expected; the reader copies nothing, so there is no buffer risk.
- <a id="n-15"></a>**N-15** Reply when no section gives an action for a Command in a state? Recommendation: NAK 0x02 (Command Not Expected), no state change. Confidence: 85%. Review necessary: no, Table 25 defines 0x02 for this case and a NAK ends no session. AMB-M2-124-05, AMB-M2-124-09, AMB-M2-124-39. REQ-NET-SES-004.
- <a id="n-16"></a>**N-16** Bye to an address with no session entry (0x05, 0x07, 0x40, 0x41, 0x45, 0x06): repeat it with a Pending Bye entry? Recommendation: one Bye for each received Command or UDP payload, no entry, no repeat. Confidence: 85%. Review necessary: yes, 6.16 says that a Bye should be repeated. AMB-M2-124-43. REQ-NET-INV-012, REQ-NET-INV-007, REQ-NET-INV-015, REQ-NET-INV-023, REQ-NET-INV-029, REQ-NET-RST-011, REQ-NET-DATA-003, REQ-NET-AUTH-027. Review done: a full table has no entry for Pending Bye; the peer repeats its Command and gets a new Bye each time.
- <a id="n-17"></a>**N-17** UMP Data, Retransmit Request or Retransmit Error in Pending Bye, and Retransmit Commands in Pending Session Reset? Recommendation: discard, no second Bye. Confidence: 75%. Review necessary: yes, it reads a "shall" (Bye 0x05) as "discard" in these states. AMB-M2-124-54, AMB-M2-124-59. REQ-NET-DATA-003. Review done: in Pending Bye a Bye is already in progress; in Pending Session Reset a Bye ends an active session and the requested numbers are void after the reset.
- <a id="n-18"></a>**N-18** Invitation Reply: Accepted or Pending at a Client in Pending Session Reset or Pending Bye? Recommendation: ignore. Confidence: 80%. Review necessary: no, the literal Bye 0x06 would end an active session. AMB-M2-124-40. REQ-NET-INV-023, REQ-NET-INV-029.
- <a id="n-19"></a>**N-19** Bye Reason at the Invitation timeout? Recommendation: 0x80 (Invitation Canceled). Confidence: 90%. Review necessary: no, 6.4 gives 0x80 with "shall". AMB-M2-124-07. REQ-NET-INV-011, REQ-NET-AUTH-038.
- <a id="n-20"></a>**N-20** Malformed Invitation? Recommendation: csd1 more than pl gives NAK 0x03; an empty name or id gives Bye 0x07. Confidence: 85%. Review necessary: no, Table 27 gives the 0x07 example for this case. AMB-M2-124-18. REQ-NET-INV-001, REQ-NET-INV-007.
- <a id="n-21"></a>**N-21** Repeat interval: default and range check? Recommendation: 500 ms; the configuration refuses values outside 300 ms to 2000 ms. Confidence: 75%. Review necessary: yes, it makes a "recommended" range into a hard limit. AMB-M2-124-07. REQ-NET-SES-006 (used by REQ-NET-INV-009, REQ-NET-AUTH-037, REQ-NET-RST-004, REQ-NET-BYE-007). Review done: libnetmidi2 500 ms; Windows MIDI Services 1000 ms (500 ms for Bye); a sans-IO test gives the time, so tests need no short interval.

### Other implementations (USB-MIDI), survey of 2026-10-17

The full notes with file and line evidence are not in the repository.
TU = TinyUSB (MIT), LXH/LXG = Linux host sound/usb and gadget f_midi/f_midi2 (GPL-2.0, read for behaviour only),
WIN = Windows MIDI Services (MIT), EMB = embassy-usb (MIT/Apache-2.0), UMI = usbd-midi (MIT), AMD/AMT = AmeNote
usbMIDI2DescriptorBuilder / tusb_ump (WIN and AMT share author and structure: not independent). No Apple source.

- 1.0 MS header wTotalLength: TU, EMB, UMI, AMD count the endpoints (Appendix B 0x41 style); LXG f_midi counts header
  and Jacks (Table 6-2); f_midi2 a third value. No host reads it. 2.0 MS header: every writer 0x0007; hosts ignore it.
- Cable to Jack: LXH and EMB host use the position in baAssocJackID; WIN the n-th Embedded Jack in descriptor order;
  writers keep both equal. A cable with no Jack is dropped. Cable n = Group n (WIN, AMT; LXG default).
- CIN: real time sent as CIN 0xF (LXH, LXG, EMB, UMI) or 0x5 (TU, AMT, WIN by default; a WIN source comment says that
  some devices ignore it when sent as CIN 0x5); real time inside SysEx in its own packet; F4/F5 not sent by 4 of 6;
  status repeated (no running status) by LXH/LXG; unused bytes zero; readers take the length from the CIN and ignore
  CIN 0x0/0x1.
- Group Terminal Blocks: only by GET_DESCRIPTOR wValue 0x2601 (Standard request to the interface), never inline;
  hosts read 5 bytes, then wTotalLength; devices send min(wLength, total), stall on Alt 0 or a wrong interface.
- bMIDIProtocol written: 0x11 (TU, LXG, AMD), 0x03 (LXG), 0x00 (AMT), 0x01 (WIN for MIDI 1.0 devices). LXH ignores 0x00
  and unknown values. Function Blocks win over Group Terminal Blocks (LXH, WIN).
- UMP over USB: little-endian words; TU and WIN keep each UMP whole in a packet; LXH, LXG, WIN, TU hold a partial UMP;
  bytes beyond a multiple of 4 are cut (LXH) or the transfer dropped (WIN). Bulk with bInterval 0 (LXG Alt 1 IN:
  interrupt, bInterval 1).
- Every device writer includes AudioControl (WIN does not need it). No Element descriptors, no Transfer endpoints.
- No implementation drops a UMP by Group on Alt 1. In conversion to 1.0 packets, a Group with no cable and MT 0x0/0xF
  are dropped.
- Hosts select Alt 1 when it has bcdMSC 0x0200 (LXH, WIN, TU host; TU host falls back to Alt 0).
- iJack 0 and iBlockItem 0 mean "no string".
