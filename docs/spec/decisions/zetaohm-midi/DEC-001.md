# DEC-001 — The MIDI Association specifications are the normative authority

**Status:** accepted

The published MIDI Association specifications are the authority for every
member crate. When the code, a test or a design note does not agree with the
specification, the specification is correct and the code changes.

Each member declares the specification documents it implements as
`[[source]]` entries (kind = "protocol", with a pinned `version`) in its
requirements files. Each requirement that comes from a specification names
that source in `source` and the section, table or figure in `source_ref`.

Documents from other bodies that a member implements (USB-IF device class
specifications, the Bluetooth SIG core specification) have the same status
for the parts they define.

## Context

The earlier implementation drifted from the specification in several places
(for example the Flex Data message type value and the tempo unit). A single
rule at the workspace tier makes the specification the tie-breaker for every
member.

## Consequences

- A requirement without a specification reference is a derived requirement
  (kind = "derived") and must say so.
- A member decision is necessary only where the specification is ambiguous or
  where the member selects between specification revisions.
- Test vectors come from the specification text first. Vectors from other
  implementations are a secondary check only.
- A newer specification revision is adopted by a change to the pinned
  `version`, not silently.
- A decision never restates or re-decides what a specification already
  defines. Where a specification defines a behaviour, a requirement cites it
  (`source`, `source_ref`) and no decision is written. A decision records
  only choices the specifications leave open: implementation and API design,
  the interpretation of an ambiguous or silent section, and the selection of
  a specification revision. A decision that depends on a specification rule
  names the section in `source_ref` and does not repeat the rule.

## Alternatives

- One decision in each member: rejected. The rule is the same for every
  member; the per-member part (which documents) is data, so it goes in each
  member's `[[source]]` table.
- Follow an existing implementation (for example the `midi2` crate): rejected.
  Other implementations can contain errors and are not normative.

## Verification

Review: each requirement that cites a specification has `source` and
`source_ref`. Tests cite the specification section they check.
