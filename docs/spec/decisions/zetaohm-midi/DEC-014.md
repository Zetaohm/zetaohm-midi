# DEC-014 — USB-MIDI in a new sans-IO crate zmidi-usb; stack adapters in separate crates

**Status:** accepted

USB-MIDI (USB Device Class Definition for MIDI Devices, v2.0 and v1.0) goes in a new workspace crate
`zmidi-usb`, the seventh specdev member (library-api). It is `no_std` with no `alloc` (DEC-002),
synchronous and sans-IO (DEC-004): it has no USB stack dependency, and the caller's USB stack moves
the bytes.

Scope of `zmidi-usb`:
- USB-MIDI 2.0 data: UMP words to and from USB packet bytes, each 32-bit word with the least
  significant byte first (v2.0 3.2.2); a UMP is kept whole in one USB packet where possible (3.2.3);
  a UMP that a transfer cuts is held until its end arrives.
- USB-MIDI 1.0 data: the 4-byte USB-MIDI Event Packets (Cable Number, Code Index Number) to and
  from UMP, with the MIDI 1.0 bytes of the byte stream codec of `zmidi-io`. The reader uses the
  `zmidi-io` byte stream reader. The writer maps each UMP straight to its Event Packets; its packets
  hold the bytes that the `zmidi-io` byte stream writer (UmpToBytes, running status off) gives for
  that UMP, and a property test against UmpToBytes verifies this (addendum of 2026-10-22).
- Descriptors: the device side writes the MIDI Streaming interface descriptors of Alternate Setting
  0 (USB-MIDI 1.0) and Alternate Setting 1 (USB-MIDI 2.0) and the Group Terminal Block descriptors
  into a caller buffer; the host side reads them.

`zmidi-usb` depends on `zmidi-ump` and `zmidi-io`; `midi` re-exports it.

USB stack adapters are separate Cargo crates, not specdev members: `zmidi-usb-embassy`
(`embassy-usb`) and `zmidi-usb-device` (`usb-device`, for firmware without embassy). They connect the
codecs to the stack and contain no protocol logic (DEC-004). A firmware that does not use embassy
does not depend on `embassy-usb`.

This decision replaces the USB parts of DEC-003 (USB-MIDI 2.0 class in `zmidi-io` on the
`embassy-usb` builder; `usb-device` rejected) and of DEC-004 (USB packet codec in `zmidi-io`). The
BLE and UART parts of DEC-003 and DEC-004 do not change.

## Context

USB-MIDI 2.0 3.1.1: a USB-MIDI
2.0 device should give a USB-MIDI 1.0 function on Alternate Setting 0 and the 2.0 function on
Alternate Setting 1, so both data formats and both descriptor sets are necessary. `embassy-usb` has a
USB-MIDI 1.0 class that moves raw packets only: no CIN conversion and no 2.0 descriptors. A firmware
without embassy must not need `embassy-usb`, and both kinds of firmware get adapters and example
firmware (roadmap).

## Consequences

- The workspace gets a seventh specdev member with its own spec.toml, specs/ and gates, including a
  bare-metal gate (DEC-002). REQ-USB-001 (M2-104 Appendix I) moves from zmidi-io to zmidi-usb.
- Catalogue rows of the USB-MIDI documents have the owner `zmidi-usb`; UMP message content stays with
  `zmidi-ump`; the MIDI 1.0 byte stream stays with `zmidi-io`; USB enumeration, control transfers and
  the endpoint hardware are `device` (the stack).
- The adapter crates come later (roadmap). Each one adds its stack as a dependency.
- HAL support differs: `usb-device` covers most STM32 parts (stm32-usbd, synopsys-usb-otg); esp-hal
  1.1 gives a `usb-device` bus for ESP32-S2/S3, but the esp-hal 1.2 documentation shows only an
  `embassy-usb` driver. The non-embassy path for ESP32 is open (roadmap).

## Alternatives

- All USB code in `zmidi-io`, as DEC-003 said: rejected. One crate for each specification document
  (DEC-006, DEC-012), and a firmware without embassy must not pull `embassy-usb`.
- Adapters as Cargo features of `zmidi-usb`: rejected. The codec crate stays free of stack
  dependencies, and a stack update changes only one small crate.
- A direct CIN-to-UMP converter with no `zmidi-io` dependency: rejected. It repeats the System
  Exclusive splitter and the MIDI 1.0 to MIDI 2.0 conversion of the `zmidi-io` byte stream codec.
  The reader keeps the `zmidi-io` reader for the lenient rules of REQ-USB-EVT-010.
- Addendum of 2026-10-22: the writer direction (UMP to Event Packets) does
  not go through a byte stream. It uses the word API `midi2_to_midi1` of `zmidi-ump` for Message
  Type 0x4, so it repeats no translation; it gives the same bytes as UmpToBytes. It saves 332 to
  732 B of flash (OPT-050 option 1). The old byte path stays in the tests as the
  oracle of `prop_writer_matches_byte_stream_writer`.
- Addendum of 2026-10-23: a Cargo feature `alt0` of `zmidi-usb` (on by default, DEC-017;
  the adapters forward it) holds the Alternate Setting 0 data path. With it off, Alternate Setting 0 stays (USB
  2.0: the default setting of an interface is 0; Linux 6.5+ needs two settings for USB MIDI 2.0) but has no
  Jack and no endpoint, and the link moves no data there (REQ-USB-GEN-014). It saves about 3,000 B of flash
  (OPT-050 option 3, variant B). A host with only a USB-MIDI 1.0 driver shows no port; macOS 27
  selects Alternate Setting 1 (T-015); Windows 11 and Linux 6.5+ are not tested (T-015). The full function
  (feature on) is the default, so the "should" of USB-MIDI 2.0 3.1.1 holds for the default build.

## Verification

`zmidi-usb` builds for the bare-metal target with `--no-default-features` and has no dependency on
`embassy-usb`, `usb-device` or a HAL crate. The descriptor examples of USB-MIDI v2.0 Appendix B and
v1.0 Appendix B are test vectors.
