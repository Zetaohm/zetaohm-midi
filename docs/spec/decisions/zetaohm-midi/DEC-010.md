# DEC-010 — Property Exchange: resolutions of M2-103 conflicts D-1 to D-4

**Status:** accepted

`zmidi-ci-pe` resolves four confirmed M2-103-UM v1.2 conflicts
(the ambiguity register, D-1 to D-4) as follows:

1. D-1 "full" Subscription update: the Property Data is the complete value in
   the Reply to Get Property Data format (Table 39). The 11.3 text (Partial SET
   format, citing a wrong section) is not followed.
2. D-2 Flow Control on Get: the Initiator sends a MIDI-CI ACK after every
   reply Chunk, the last one included (15.2). A Responder completes the
   transaction without waiting for the last ACK, so a peer that follows
   Figure 6 still works.
3. D-3 Flow Control on Set: when the ResourceList gives "fcOnSet": true, the
   Initiator writes "flowControl": true in the Inquiry: Set Property Data
   header and waits for an ACK before each further Chunk. A Responder that does
   not support Flow Control for the Resource replies with status 406 (or 407)
   in the Reply to Set Property Data (15.3 says "Reply to Inquiry Get"; read
   as an error in the text).
4. D-4 "msg": a received "msg" longer than the header buffer (DEC-007) is
   truncated at a character boundary and marked as truncated; the reply status
   and the other header fields are kept. The writer limits "msg" to 512 bytes
   after escaping, as Table 14 gives for "message", and returns an error above.

## Context

The PDF pages confirm each conflict (M2-103 p41-42, p69-71, p28/p60-61, p28/p53).
JUCE, the MIDI 2.0 Workbench and ktmidi all use the Reply to Get format for
"full"; only the Workbench implements Flow Control, and it does 2 and 3 as
above. None limits header string lengths.

## Consequences

- The M2-103 requirements for 11.3, 15.2, 15.3 and 13.1 use these readings and
  name the conflicting section.
- Interop with the Workbench for Flow Control; JUCE answers an ACK with
  NAK 0x00, which the Initiator must tolerate.
