# DEC-005 — Requirements structure: spec catalogue, singular requirements, acceptance level

**Status:** accepted

Requirements are kept at three levels, following protocol conformance practice
(a requirements catalogue with test purposes, ISO/IEC 9646 and ETSI) and the
requirement properties of ISO/IEC/IEEE 29148 (singular, verifiable, traceable).

1. Catalogue (not published: it quotes the specifications): one file for each
   specification document and version, with one row for each
   normative statement (shall, should, must) and each encoding rule of a
   specification document, with a stable id `<doc>/<section>/<nn>` (for example
   `M2-104/7.2.2.1/01`), the quote, the owner member, and the requirement id
   that covers it or `N/A` with a reason.
2. Requirements (specdev, in the owner member):
   - one requirement for each behaviour statement (shall, must, should);
   - one requirement for each message format (fields, ranges, reserved values),
     which refers to the specification figure and the Appendix F table;
   - `source_ref` names the specification section and the catalogue ids the
     requirement covers;
   - a "should" statement keeps the word "should"; when a member does not
     follow it, a member decision records why;
   - rows with owner `device` or `informative` get no requirement.
3. Acceptance: the M2-100 minimum compatibility rules are top-level
   requirements, and the MIDI 2.0 Workbench Compliance Checklist is an
   acceptance test for the example firmware.

Wording of requirement text (ISO/IEC/IEEE 29148 and EARS):
- Obligation words are the MIDI conformance words (Table 2 of each MIDI 2.0
  document), in lowercase: "shall", "shall not", "should", "should not",
  "may". The words "must", "will", "can" and "might" (Table 3) are never
  obligation words. RFC 2119 capitals are not used.
- Each clause uses the word of the catalogue row it covers. A row with no
  conformance word (an encoding rule, or a statement that describes a defined
  format or procedure) gives "shall", but only where no row with a
  conformance word covers the same clause: an overview sentence or a figure
  does not raise a "should" to "shall". A "may" row gives a permission for
  the sender ("may") or an obligation for the receiver ("shall accept"). An
  "avoid" gives "should not". When rows with conformance words give
  different words for the same clause, the stronger word applies and the
  requirement names the section with the other word.
- Each requirement names its actor ("the crate", "the reader", "the
  writer", "the translator", "the endpoint", "the JR sender", "the clip
  writer", …) and follows one EARS pattern: "The <actor> shall …"; "When
  <trigger>, the <actor> shall …"; "While <state>, …"; "If <condition>, then
  the <actor> shall …"; "Where <feature>, …".
- A message-format requirement (one for each message, see 2) is one
  sentence "The crate shall read and write <message>: <fields>", and may add
  writer and reader clauses for ranges and reserved values.
- Requirements are necessary, singular, unambiguous, complete, feasible,
  verifiable, correct and traceable (29148), and avoid vague words ("as
  appropriate", "if possible", "etc.", "easy", "fast", "it"/"this" with no
  clear target). Wording that a specification quotation needs (for example
  "as close as possible") is kept.

## Context

The M2-104-UM extraction gave 697 catalogue rows. One requirement for each row
would give about 600 requirement files, and a test for one message format
would need about five `verified_by` links. The specifications do not define a
requirement structure for implementations.

## Consequences

- Every catalogue row ends with a requirement id or `N/A` and a reason, so a
  missing requirement is visible.
- Each test verifies one requirement; through `source_ref`, it traces to the
  catalogue rows and to the specification section.
- The same structure applies to every specification document and member.

## Alternatives

- One requirement for each catalogue row: rejected. Too many files, and one
  format test would need several links.
- One requirement for each message family: rejected. Not singular; a failed
  test would not show which rule failed.
