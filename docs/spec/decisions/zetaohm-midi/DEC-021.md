# DEC-021 — Standard MIDI File 1.0 (RP-001) reader and writer in zmidi-file, no Cargo feature

**Status:** accepted

`zmidi-file` reads and writes Standard MIDI Files 1.0 (RP-001, revised February 1996), formats 0, 1 and 2,
next to the MIDI Clip File. The SMF code has three new modules in `zmidi-file`:
- `SmfFormat`: the chunk types `MThd` and `MTrk`, the variable-length quantity (at most 0x0FFFFFFF, four
  bytes), the division (ticks per quarter-note, or SMPTE frames per second and ticks per frame) and the
  typed meta-events of RP-001 pages 8 to 10.
- `SmfReader`: sans-IO over a borrowed byte slice. It reads the header chunk (and honors a length larger
  than 6), gives the track chunks in file order and skips alien chunks, and gives the events of each
  track (delta-time, absolute ticks, channel message, sysex event or meta-event) with running status.
- `SmfWriter`: writes into a caller buffer, as `ClipWriter` does. It writes the header chunk, the track
  chunks and End of Track, patches the chunk lengths and the track count, and uses running status
  (on by default, off by a setting).

Channel messages are MIDI 1.0 Channel Voice messages. The reader gives each one as its status and data
bytes and as a UMP MT 0x2 word with a group from the caller; the writer takes either form. The SMF code
asks for no `zmidi-ump` message family. Sysex events stay bytes; the caller converts them to UMP with
`zmidi-io` if it needs to.

The SMF code has no Cargo feature in `zmidi-file`. When the SMF part goes into the C ABI, `zmidi-ffi`
gets its own feature for it, as for the other parts (DEC-019).

The conversion from SMF to the MIDI Clip File and back (meta-events to Flex Data, ticks to Delta
Clockstamps) is not in this decision. It needs its own design.

## Context

Before this decision `zmidi-file` had the MIDI Clip File only, so a MIDI 1.0-only user had no file format.
SMF comes before the release, with a reader and a writer as the first scope.

Feature question: a scratch probe (thumbv7em-none-eabi, opt-level "s", 2026-10-25) showed that unused
`zmidi-file` code costs 0 B (no `zmidi_file` symbol in the binary with or without LTO). The link of
`zmidi-file` costs 520 B (fat LTO) to 4,240 B (no LTO) because it asks for `zmidi-ump/full` (OPT-039).
A Cargo feature for SMF does not change that cost, and OPT-052 rule 2 keeps features at
the central dispatch points. In the C ABI the linker keeps every exported function, so there a feature
is necessary.

## Consequences

- A new catalogue for RP-001 (DEC-005), new source `rp-001` and requirements
  `REQ-SMF-*` in `zmidi-file`; RP-001 ambiguities go in the ambiguity register (AMB-RP-001-*).
- RP-001 has no conformance-word table. As in the M1 catalogue, "must" rows that describe the byte
  format are rules ("shall"), and "should" stays "should" (DEC-005).
- The reader rejects what RP-001 forbids (an event with no status and no running status, a data byte
  above 0x7F, a variable-length quantity of more than four bytes, a channel message inside a
  multi-packet sysex message, a chunk cut by the end of the data). It gives what RP-001 does not forbid
  (unknown formats, unknown meta-events, a track count that differs from the chunks found).
- `zmidi-file` keeps `zmidi-ump` with `full` until OPT-039 is done; the SMF modules do not add to it.
- The `midi` facade re-exports the SMF types through `zmidi-file`; no new crate, no new feature.
- Later work: SMF to Clip conversion, the `zmidi-ffi` part and the bindings (roadmap).

## Alternatives

- A Cargo feature `smf` in `zmidi-file`: rejected; it saves compile time only (probe above).
- A new crate `midi-smf`: rejected; RP-001 and M2-116 are both MIDI file formats, and `zmidi-file` already
  has the "reader over a borrowed slice, writer into a caller buffer" model.
- SMF and Clip conversion in the first step: deferred (2026-10-25).
- Channel messages as bytes only: rejected; the library model is UMP inside, and the MT 0x2 word costs a
  few instructions.

## Verification

- The RP-001 page 12 to 14 example files (format 0 and format 1) are test vectors for the reader and the
  writer, byte for byte, with the running status of the example.
- The variable-length quantity table of RP-001 page 2 is a test vector in both directions.
- proptest: write then read gives the same events; the reader never panics on any input bytes.
- The bare-metal gate (DEC-002) builds `zmidi-file` with the SMF modules.
