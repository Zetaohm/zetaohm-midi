# DEC-006 — Property Exchange (M2-103) in a new crate zmidi-ci-pe; framing stays in zmidi-ci

**Status:** accepted

MIDI-CI Property Exchange is split along the specification documents:
- `zmidi-ci` implements M2-101-UM, including the Property Exchange message
  framing (Universal SysEx Sub-ID#2 0x30 to 0x3F): Request ID, Length of
  Following Header Data, Header Data bytes, Number of Chunks, Number of This
  Chunk, Length of Following Property Data, Property Data bytes.
- A new workspace crate `zmidi-ci-pe` implements M2-103-UM: the meaning of the
  Header Data (JSON), status codes, Mcoded7, zlib compression, Resources and
  subscriptions. It depends on `zmidi-ci`; `zmidi-ci` does not depend on it.

`zmidi-ci-pe` is a specdev member (library-api) like the other library crates,
and `midi` re-exports it.

## Context

The user chose MIDI-CI scope C (minimum, Profiles and Property Exchange) on
2026-10-14 and accepted this split in chat. M2-101 Tables 33 and 34 contain
only the framing; M2-103 defines the header and data semantics. The project
keeps one crate for each specification document (zmidi-ump: M2-104, zmidi-ci:
M2-101, zmidi-file: M2-116).

## Consequences

- A firmware that uses only Discovery or Profiles does not compile the JSON,
  Mcoded7 or zlib code and dependencies.
- The DEC-002 rules for Property Exchange (DEC-007) apply to `zmidi-ci-pe`
  only; `zmidi-ci` stays no_std with no alloc and no PE-specific dependency.
- M2-103 catalogue rows have the owner `zmidi-ci-pe`; M2-101 PE framing rows
  have the owner `zmidi-ci`.
- The workspace gets a fifth specdev member, with its own spec.toml, specs/
  and gates.

## Alternatives

- An optional `pe` Cargo feature in `zmidi-ci`: rejected. Same dependency
  isolation, but two specification documents in one spec member and a less
  clear DEC-002 boundary.
- All PE code in `zmidi-ci` with no feature: rejected. Every MIDI-CI user would
  compile the JSON and compression code.
