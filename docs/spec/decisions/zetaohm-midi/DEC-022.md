# DEC-022 — Full MIDI 1.0 support: placement, one feature per part, MIDI 1.0-only builds, no MIDI 2.0 cost

**Status:** accepted

The library gives full MIDI 1.0 support next to MIDI 2.0: the meanings of the MIDI 1.0 messages (M1 v4.2.1 with
RP-015 and RP-018), the receiver and sender behaviour, the Universal System Exclusive messages, MIDI Time Code
(RP-004/RP-008), MIDI Machine Control (RP-013), MPE (M1-100), the File Reference message (CA-018) and the 3D Sound
Controllers (RP-049).

Placement:
- `zmidi-ump`: the value meanings with no state (controller numbers and classes, switch reading, RPN numbers and
  their value conversions, Note On velocity 0, Song Position Pointer to clocks), and a public RPN/NRPN assembler that
  the 1.0 to 2.0 translator and the MIDI 1.0 parameter receiver both use. The bank state is not shared: the
  translator clears its bank after a Program Change (REQ-XLATE-022), a MIDI 1.0 receiver keeps it.
- `zmidi-io`: the receiver and sender states on MIDI 1.0 messages (channel mode, controllers, parameters, bank and
  program, MPE, 3D controllers, clock sync, Active Sensing, merger) and a typed reader and writer on bytes. The states
  take the typed messages, so they work for 5-pin DIN, USB-MIDI 1.0, BLE-MIDI and Message Type 0x2 UMPs.
- A new member `zmidi-sysex`: the Universal System Exclusive messages over one complete message as `&[u8]`
  (transport-independent), MTC (Quarter Frame reader and generator, Full Message, User Bits, cueing) and MMC. MTC and
  MMC share one time code type.

Features: each part is one Cargo feature that gates its module and its arm at each dispatch point, in `full` (on by
default, DEC-017); a feature that needs another turns it on. Stateless meanings stay with the feature of their message
family. The typed MIDI 1.0 messages keep the UMP word (Message Type 0x2) inside; their API shows no UMP Group.

MIDI 1.0-only builds come first: every MIDI 1.0 function builds with no MIDI 2.0 code. `zmidi-usb` gets a feature
`alt1` (the USB MIDI 2.0 Alternate Settings, `alt1 = ["zmidi-ump/full"]`), `zmidi-ble` a feature `midi2-protocol`
(`["zmidi-io/midi2-protocol", "zmidi-ump/full"]`), `zmidi-file` a feature `clip` (the MIDI Clip File), the facade
`zmidi` the group features `midi1` and `midi2`, and `zmidi-io` a separate SysEx byte reader that gives complete
messages to `zmidi-sysex`. CI builds a MIDI 1.0-only firmware with size budgets and fails when a MIDI 2.0 module links.

Rule R0: no part of this work increases the flash, the RAM or the CPU time of a MIDI 2.0 function. Gates are
compile-time only; with the MIDI 2.0 features on, the code is the same as before (the pattern of the `zmidi-usb`
feature `alt0`); a new MIDI 1.0 path that needs a branch is a separate type, not a run-time flag in an existing hot
path. Two correctness fixes in the 1.0 to 2.0 translator are accepted exceptions, each with its measured cost: the
RPN/NRPN selection becomes null at Reset All Controllers (AMB-RP-015-01), and an MPE Configuration Message is sent at
Data Entry MSB, as it has no LSB (AMB-M1-100-19).

Scope choices: the first MMC tier `mmc-transport` is Guideline Minimum Set 1 plus PLAY and PAUSE (AMB-RP-013-02).
Master Fine/Coarse Tuning and GM2 System On are in scope; DLS-1, Controller Destination, Key-based Instrument
Control, SP-MIDI MIP and Global Parameter Control are not (AMB-RP-028-02); MIDI Show Control gets only its raw
sub-ID. The 7-bit codec of File Dump and of Property Exchange (REQ-PE-ENC-008) is one shared module. The work stops
after the common parts (the core states, MPE, the common Universal SysEx messages, `mtc`, `mmc-transport`); each later
part (merger, 3D controllers, notation, MTC cueing, full MMC, Sample Dump, File Dump, File Reference, the chart
capability sets) starts only after a value report to the user and the user's decision.

## Context

Before this decision the MIDI 1.0 support was the byte-stream codec, USB-MIDI 1.0, BLE-MIDI, Standard MIDI Files and
the MIDI 1.0 messages in UMP form; the MIDI 1.0 catalogue covered only the byte-stream part of M1. The full catalogues
(1416 rows, 764 of them library work, 167 ambiguity items) and the measurements of 2026-11-02 showed:
- a 5-pin DIN build has no MIDI 2.0 code, but a USB-MIDI 1.0-only function still links the USB MIDI 2.0 data path,
  the Group Terminal Block code, the UMP packet code and the 2.0 to 1.0 translator (7,868 B of class flash with
  fixed descriptors, against 8,052 B with both Alternate Settings), because the class selects the setting at run time;
- a BLE-MIDI 1.0 reader keeps the 1.0 to 2.0 translator (934 B named in the word reader) for the same reason;
- `zmidi-usb`, `zmidi-ble` and `zmidi-file` ask for MIDI 2.0 families of `zmidi-ump` in every build.
Rust users of MIDI 1.0 have `wmidi` and `midi-msg`; the value of this library is MIDI 1.0 and 2.0 together, `no_std`
with no allocation and size budgets, and the C, Python, TypeScript and Dart bindings.

## Consequences

- A new specdev member `zmidi-sysex` (public crate, no MIDI version in the name).
- New Cargo features in `zmidi-usb` (`alt1`), `zmidi-ble` (`midi2-protocol`), `zmidi-file` (`clip`), `zmidi-io`
  (one per state part), `zmidi-sysex` (one per message family) and the facade (`midi1`, `midi2`, part `sysex`), each
  confirmed by name in the step that adds it, as DEC-017 does. Default builds keep today's feature unification, so a
  downstream build (FLXS1 pins a git rev) sees no change.
- The CI feature matrix groups the features that need each other (`--group-features`) and runs `zmidi-sysex` at depth
  1 on each push and at depth 2 in the weekly run.
- Each part of the common set lands with its C ABI functions (a new ABI minor version) and its Python, TypeScript and
  Dart wrappers; the MIDI 1.0-only C ABI build comes with the first core part.
- Requirements: one for each message family or rule, not one for each catalogue row (about 120 to 180).
- Tests use corrected vectors where a specification example is wrong (AMB-M1-45, AMB-M1-46, AMB-M1-100-04,
  AMB-M1-100-08, AMB-RP-049-01, AMB-RP-049-02).
- The USB-MIDI 1.0 class stays about 4x the size of `usbd-midi` after `alt1` (OPT-056).

## Alternatives

- A fourth new crate for the channel states (mode, controllers, parameters, MPE, 3D): clean boundaries, but one more
  crate to publish and bind for about 4 KB of code. Rejected by the user.
- Channel states and MPE in `zmidi-ump`: no new dependency for `zmidi-net` and `zmidi-file`, but `zmidi-ump` becomes a
  state crate. Rejected.
- A byte-native second set of MIDI 1.0 message types: no UMP code at all, but about 1 KB more and two types for one
  message. Rejected; the UMP word form is not MIDI 2.0 Protocol code.
- Features only at the dispatch points (the DEC-017 rule): the linker removes unused code, but the API of a build then
  shows parts that the user did not select. Rejected by the user for these parts.
- MIDI 1.0-only builds after the new parts: each new part would land in a build that CI does not measure. Rejected.
- Exactly Guideline Minimum Set 1 for `mmc-transport`: most DAWs send PLAY. Rejected.
- Two copies of the 7-bit codec: no dependency, but two copies to test. Rejected by the user.

## Verification

- `scripts/size-check.py` and `scripts/speed-check.py` before and after each change: no existing job higher in flash,
  RAM, stack or instruction count (R0); for the default-feature jobs the goal is the same ELF. The two translator
  exceptions record their measured cost.
- New size jobs for the MIDI 1.0-only USB class (fixed and run time) and BLE readers, with budgets.
- A CI job builds the facade with `--no-default-features --features midi1` for `thumbv7em-none-eabihf` and fails when
  a MIDI 2.0 module name is in the ELF.
- The feature matrix for the new features (grouped as above).
- Specification vectors first, corrected vectors where the specification is wrong.
