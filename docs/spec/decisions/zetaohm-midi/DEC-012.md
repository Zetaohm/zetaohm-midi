# DEC-012 — Network MIDI 2.0 (M2-124) in a new sans-IO crate zmidi-net

**Status:** accepted

Network MIDI 2.0 (UDP), M2-124-UM v1.0.1, goes in a new workspace crate `zmidi-net`, a sixth specdev
member (library-api). It is `no_std` with no `alloc` (DEC-002) and sans-IO, like zmidi-ci (DEC-009):
the caller owns the UDP socket, the clock and the random numbers (nonces, Session tokens).

Scope of `zmidi-net`:
- the UDP payload format: signature, command packets, command codes, the UMP Data command;
- the Host and Client Session state machines: invitation, authentication (DEC-013), reset, ping,
  bye, NAK;
- UMP Data commands with sequence numbers, Forward Error Correction and retransmit, with buffers of
  fixed size (const generics);
- DNS-SD record data only: build and read the PTR, SRV and TXT record contents and names. There is
  no mDNS responder; the platform or the application provides it.

`zmidi-net` depends on `zmidi-ump`; `midi` re-exports it.

## Context

The user chose Network MIDI 2.0 as the next area on 2026-10-15 and accepted recommendations N1
(crate) and N3 (DNS-SD scope). M2-124 4.1: "User applications may connect to OS-provided mDNS
services to advertise a Host service, or to implement their own mDNS service." The project keeps one
crate for each specification document (DEC-006).

## Consequences

- M2-124 catalogue rows have the owner `zmidi-net`; rules about UMP message content stay with
  `zmidi-ump`; sockets, IP addresses and the mDNS responder are `device`.
- The workspace gets a sixth specdev member with its own spec.toml, specs/ and gates, including a
  bare-metal gate (DEC-002).

## Alternatives

- Put Network MIDI in zmidi-io: rejected. One crate for each specification document; zmidi-io stays
  the transport-neutral layer.
- A full mDNS responder in the crate: rejected. It needs sockets and timers, it is platform-specific,
  and the specification permits the OS services.
