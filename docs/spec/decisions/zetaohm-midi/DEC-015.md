# DEC-015 — USB adapters: async embassy-usb with distinct endpoint pairs; usb-device 0.3

**Status:** accepted

The USB stack adapters of DEC-014 are two Cargo crates, not specdev members: `zmidi-usb-embassy`
(`embassy-usb` 0.6, `embassy-sync` 0.8) and `zmidi-usb-device` (`usb-device` 0.3). Both are `no_std`
with no `alloc` (DEC-002). They contain no protocol logic (DEC-004):
- descriptors: the bytes of zmidi-usb `write_function`, given to the stack builder or descriptor
  writer descriptor by descriptor;
- the Group Terminal Block request: zmidi-usb `handle_gtb_setup`;
- data: zmidi-usb `MidiLink` (one MIDI OUT and one MIDI IN endpoint for each Alternate Setting).

Both adapters write Alternate Setting 0 (USB-MIDI 1.0) and the USB MIDI 2.0 settings (USB-MIDI v2.0
3.1.1 p. 15, REQ-USB-GEN-001): the USB transport is not backward compatible, and a host with only a
USB-MIDI 1.0 driver uses Alternate Setting 0.

`zmidi-usb-embassy`:
- Each endpoint address is in exactly one Alternate Setting. A configuration that gives one address
  to two settings is refused with an error. The adapter selects the endpoint pair of the current
  setting. A helper gives the default layout: OUT 1 and IN 1 on Alternate Setting 0, OUT 2 and IN 2
  on Alternate Setting 1.
- Async. A `State` holds the `MidiLink` in a blocking `Mutex<M: RawMutex, RefCell<_>>`. The mutex is
  held only while the synchronous codec runs, never across an `.await`. A `Handler` reports the USB
  reset, the configuration change and SET_INTERFACE to the link (`report_setting` with the Group
  mask and wMaxPacketSize of the setting) and answers the Group Terminal Block request. `split()`
  gives a `Sender` and a `Receiver` for two tasks.
- The Interface Association Descriptor follows `embassy_usb::Config::composite_with_iads`.

`zmidi-usb-device`:
- Synchronous `UsbClass`, used with `UsbDevice::poll`. One endpoint address can be in more than one
  Alternate Setting (as in USB-MIDI v2.0 Appendix B) when its transfer type and wMaxPacketSize are
  the same in each setting: one hardware endpoint has one type.
- `reset` reports the USB reset; SET_CONFIGURATION, seen in `control_out` and not accepted there,
  reports the configuration change; `set_alt_setting` reports the setting. The adapter writes a
  packet only when the IN endpoint is free (`endpoint_in_complete`), so no packet is lost.
- The Interface Association Descriptor follows `UsbDeviceBuilder::composite_with_iads` (default
  off), as on embassy.

Both adapters:
- take the interface names as `&str`, get the string indexes from the stack, write them into the
  `FunctionConfig` and answer the string requests;
- send a zero-length packet after a packet of exactly wMaxPacketSize when no more data is ready, so
  the host sees the end of the bulk transfer.

## Context

`embassy-usb` 0.6.0 enables the endpoints on SET_CONFIGURATION and
SET_INTERFACE with `foreach_endpoint` over the configuration descriptor: for each endpoint descriptor
it sets "enabled" from the Alternate Setting of that descriptor, so the last descriptor of an address
wins. At Alternate Setting 0, the descriptor of Alternate Setting 1 disables an endpoint that both
settings share (src/lib.rs, read 2026-10-17). USB-MIDI v2.0 has no rule that the settings use the
same endpoints; Appendix B shares them as an example. `usb-device` 0.3.2 does not enable or disable
endpoints for each Alternate Setting. The usb-device `StringIndex` has no public constructor.

## Consequences

- An embassy device uses two OUT and two IN endpoints besides endpoint 0. Host drivers (Windows,
  macOS, Linux) are not tested yet with this layout; the example firmware (roadmap section 3) tests it. If a host fails, the alternative is a fix of `embassy-usb`.
- The workspace gets two Cargo members; spec.toml does not list them. `scripts/adapters-check.sh`
  (bare-metal check and tests) checks them in CI, because the specdev gate script has no root
  gates (2026-10-17).
- The zero-length packet rule cites USB 2.0 5.8.3 from memory; the project has no copy of the USB 2.0
  specification.
- A change of the `embassy-usb` or `usb-device` API changes only its adapter crate.
- `zmidi-usb-device` turns on the `usb-device` feature `control-buffer-256` (128 bytes more RAM): the
  Configuration descriptor with Alternate Settings 0 and 1 is 141 bytes, more than the default
  control buffer of 128 bytes (found by the host tests, 2026-10-17).

## Alternatives

- Shared endpoints on embassy with a patched `embassy-usb` (git dependency until a release): rejected
  for now; it depends on an upstream change.
- USB MIDI 2.0 only on embassy (no Alternate Setting 0): rejected; USB-MIDI v2.0 3.1.1 asks for
  Alternate Setting 0 for USB-MIDI 1.0 hosts.
- One embassy class object with `&mut self` and `select` in one task: rejected; split() lets one task
  wait for received data while another sends. Both are async.
- Docs only, no decision: rejected.

## Verification

Host tests with a fake `usb-device` UsbBus and a fake `embassy-usb-driver` Driver: the descriptor
bytes equal those of zmidi-usb `write_function` (and the USB-MIDI v1.0 Appendix B bytes for
`zmidi-usb-device`), the Group Terminal Block answers, the events and the data path. The USB-MIDI
v2.0 Appendix B example uses IN 1 as a bulk endpoint in Alternate Setting 0 and as an interrupt
endpoint in Alternate Setting 1; `zmidi-usb-device` refuses it (one endpoint, one type), and a test
shows the refusal. Bare-metal
`cargo check` of both crates in `scripts/adapters-check.sh`. Neither crate depends on a HAL crate.
