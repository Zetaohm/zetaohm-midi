# DEC-019 — One C ABI in a new member zmidi-ffi; language bindings in bindings/<lang>

**Status:** accepted

A new specdev member `crates/zmidi-ffi` (profile `library-api`, Rust) gives the C ABI of the library.
It is `#![no_std]` with no `alloc` (DEC-002). Its manifest declares an `rlib` only; the packaging
builds give `--crate-type staticlib` or `cdylib` to `cargo rustc` (Corrosion: `OVERRIDE_CRATE_TYPE`). Cargo
features select the parts: `ump`, `io`, `ci`, `pe`, `file`, `net`, `usb`, `ble`. `zmidi-usb-device` and
`zmidi-usb-embassy` get no C ABI: they are adapters for Rust USB stacks. `extern "C"` and `unsafe`
stay in `zmidi-ffi`; the other members do not change for the FFI.

Rules of the C ABI:

1. The program gives the storage. There is no allocation and no free function. Each opaque type is
   `{ uint64_t _opaque[N]; }`, with `N` set for each pointer width (16, 32, 64 bit). A Rust
   `assert!` stops the build when a type is larger than its slot.
2. No callbacks. The library gives events that the program reads, and the program sends replies with
   separate calls (for example a `PE_GET` event, then `zmidi_ci_pe_reply`). Random numbers come
   from a generator that the program seeds at init.
3. Data in an event points into the input buffer of the program. It stays valid until the program
   uses that buffer again, or until the reply call of that event.
4. Output messages go into a buffer of the program as records `[group][len lo][len hi][bytes]`.
   Large work buffers come from the program as a scratch buffer, not from the stack of the library.
5. One cbindgen header, with `#ifdef` blocks for the parts. C names start with `zmidi_`. Array
   lengths in the header are local constants only, each checked by `assert!` against the Rust value.
   CI runs `cbindgen --verify`.
6. The library exports the real size of each opaque type. Each binding compares its struct layout
   with these sizes when it loads.

Builds: no_std with the feature `panic-handler` for bare metal and WASM; the feature `std` for host
builds (a no_std `staticlib` or `cdylib` on a host needs a panic handler and does not link on
macOS). The handler is compiled only for `target_os = "none"` and the `wasm` family, and
`panic-handler` is not a default feature, so a host test binary never gets two handlers and the
workspace gates and the feature matrix (DEC-017) build `zmidi-ffi` as the other members.

C/C++ users get a CMake package that uses Corrosion. The C tests are `crates/zmidi-ffi/tests/c/*.c`.
Each one runs from a Rust integration test (one `#[test]` for each C file), so `cargo test` runs them
and requirements name them in `verified_by`. The C tests compile as C99 with `-Werror -pedantic`, run
with ASan and UBSan, and the header also compiles as C++17.

Each language binding is a separate specdev project in `bindings/<lang>`, not a workspace member.
Order of work:

1. C and C++ (`zmidi-ffi`).
2. TypeScript: npm package over the WASM build of the C ABI (`bindings/ts`, new profile `ts-library`).
3. Dart: package over `dart:ffi` and the same WASM for the web (`bindings/dart`, new profile
   `dart-package`).
4. Python (addendum of 2026-10-22): PyO3 over the Rust crates, not ctypes over the C ABI,
   for Python classes, exceptions, iterators and a typed `.pyi` stub. Two specdev projects, as the
   specdev profile `python-ffi` defines: the Python package in `bindings/python` (profile
   `python-ffi`, built by maturin) and a Rust extension crate (profile `library-api` with the `pyo3`
   block). PyO3 `abi3-py39` gives one wheel for each platform. The extension crate needs `std`: it
   is a host-only crate, so the DEC-002 bare-metal rule does not apply to it.

Swift, C#, Kotlin, Zig and Go use the C header directly; they get examples, not packages, until a
user asks for one.

Addendum of 2026-10-22 (OPT-023, REQ-FFI-CI-009): the C features of the ci part follow the zmidi-ci
categories. `ci-device` is the Device with no category and no Initiator role; `ci-initiator`, `ci-profiles`,
`ci-property-exchange` and `ci-process-inquiry` each add `ci-device` and the zmidi-ci feature of the same
name; `ci` has all of them, so a build with `ci` (the bindings) does not change. The header guards each with
`ZMIDI_CI_DEVICE`, `ZMIDI_CI_INITIATOR`, `ZMIDI_CI_PROFILES`, `ZMIDI_CI_PROPERTY_EXCHANGE` and
`ZMIDI_CI_PROCESS_INQUIRY`; `ZMIDI_CI` selects all of them. The planned `pe` feature is
`ci-property-exchange`. Rule 3 also covers the Profile and Process Inquiry fields of an event: the program
reads them with `zmidi_ci_profile_event` and `zmidi_ci_process_event` while the message is valid;
`ZmidiCiEvent` does not change. The feature `net-auth` (DEC-013) adds Network MIDI 2.0 authentication. The
TypeScript and Dart packages build with `ci` and `net-auth` and need `ZMIDI_ABI_MINOR` 2; the Python package gives
the same ci categories and authentication through PyO3 (`zmidi-py` turns on `zmidi-net/auth`).

Addendum of 2026-10-23: the feature `ci-property-exchange` also gives the multi-Chunk Property
Exchange engine (`zmidi_ci_pe::PeEngine`, module Pe of `zmidi-ffi`) with no new feature. The program gives a second
storage `ZmidiPe` (`PeEngine<4, 256, 4, 4, 16>`: 4 transactions with 256 header bytes, 4 subscriptions, 4 peers with a
known ResourceList, 16 queued control messages) and a Resource table of at most 16 entries (`ZmidiPeResource`: one
"mediaType", no "columns"). Each `zmidi_pe_*` call takes the `ZmidiCi` too: the `CiDevice` is the `PeHost`.
`zmidi_pe_receive` reads the last event of `zmidi_ci_receive`. A program uses the engine or the one-chunk Responder
(`zmidi_ci_pe_reply`) for its replies, not both. The engine calls take the clock in microseconds, as the ci calls do,
and give milliseconds to the engine. The first step has the encodings "ASCII" and "Mcoded7"; "zlib+Mcoded7" is not
inflated (zlib window 0). The initiator calls need `ci-initiator`. `ZMIDI_ABI_MINOR` becomes 3. The flash of a link
that does not call the engine is measured before and after (`fw_ci.c`, 17,316 B with `ci-device` and
`ci-property-exchange` on 2026-10-23); a growth over about 1 KB reopens a separate feature. Measured after the
change (2026-10-23, `fw_ci.c` does not call the engine): 17,580 B (+264 B), and 24,222 B to 24,594 B (+372 B) with `ci`.

Addendum of 2026-10-23, second: zmidi-ci frees a Request ID only on `pe_end`, and the one-chunk initiator
calls never called it, so after 4 requests each new one was refused. The last Chunk of a Reply to Get, Set or
Subscription now frees the Request ID of this Device at the next `zmidi_ci_receive`, or at a `zmidi_pe_receive` of the
event (REQ-FFI-CI-021). The free waits until the event is used: `RequestTable::allocate` takes the lowest free ID, so an
earlier free lets a request between the two receive calls take the same ID, and the engine then ends the new request.
`zmidi_ci_pe_end` (REQ-FFI-CI-022) frees the ID of a request with no reply (a timeout or a NAK). `ZMIDI_ABI_MINOR`
becomes 4; the bindings add `pe_end` (Python) and `peEnd` (TypeScript, Dart). `fw_ci` with `ci`: 24,690 B (+96 B);
`ci-device` with `ci-property-exchange`: 17,580 B (no change).

Addendum of 2026-10-23, third (the USB descriptor writer and the Group Terminal Block requests; REQ-FFI-USB-006 to
-010): the feature `usb` also gives `ZmidiUsbFunction`, a zmidi-usb `FunctionConfig` with fixed capacities, because C
has no const generics: 2 USB MIDI 2.0 Alternate Settings, 4 endpoints and 16 Group Terminal Blocks (one for each Group)
in each setting, 16 block IDs for each endpoint, and only the cable-count form of Alternate Setting 0 (a full Jack
list needs caller slices with a lifetime). The storage is 103 words on 64-bit targets and 90 words on 32-bit targets
(716 B). The calls give the descriptors (Appendix B order), the endpoints for the stack, the Group Terminal mask for
the link, the Group Terminal Block sets, the device-side request handler and the host-side request writer and
reader. A broken zmidi-usb rule gives `Rejected`; the C ABI gives no reason code. The C ABI has no `FixedFunction` path
(OPT-038). `ZMIDI_ABI_MINOR` becomes 5. The bindings (2026-10-25) give one `UsbFunction` class that takes the full
description in its constructor, with the same capacities in Python, TypeScript and Dart.

Addendum of 2026-10-25, fourth (OPT-038, REQ-FFI-USB-011 and -012): C firmware with a fixed USB MIDI
function does not link the run-time writer (8,434 B on Cortex-M4F with the request handler). A host program builds
the function with the run-time calls and writes C arrays with `zmidi_usb_function_print_c` of the hand-written header
`zmidi_usb_gen.h` (stdio, host only): the descriptors with the final interface numbers and strings, the Group Terminal
Block sets, the endpoints and the Group Terminal masks. The firmware includes them and calls
`zmidi_usb_fixed_gtb_setup` (zmidi-usb `FixedFunction::gtb_setup`, no change in zmidi-usb). The probe `fw_usb_fixed` is
1,268 B flash and 76 B RAM; `scripts/ffi-check.sh` fails above 1,600 B. `ZMIDI_ABI_MINOR` becomes 6; the bindings
still need minor 5, because they do not call the new function.

Addendum of 2026-10-25, fifth (OPT-035, REQ-FFI-IO-007): `zmidi_bytes_to_ump_feed` reads many bytes in one call and
stops before a byte that could not fit, so the TypeScript and Dart `BytesToUmp.feed` make one C call for each chunk of
4096 bytes and not one for each byte. `feed` of 64 notes: TypeScript 1,736 to 59 ns for each message, Dart 596 to
198 ns. `ZMIDI_ABI_MINOR` becomes 7, and the TypeScript and Dart packages need minor 7. Cost on Cortex-M4F: 7,792 B flash
for the writer, 8,434 B with the request handler (OPT-038).

Addendum of 2026-10-24 (Dart on the web, REQ-DART-WEB-001 and -002): `dart:ffi` has no web support
(dart2wasm turns off `dart.library.ffi`), so on the web the Dart package uses the TypeScript package of `bindings/ts`
through `dart:js_interop`, not its own copy of the WASM memory layer and not the third-party `wasm_ffi` package. Each
part keeps its public API in `lib/src/<part>.dart` with the value checks in plain Dart, and selects
`lib/src/native/<part>.dart` (`dart:ffi`) or `lib/src/web/<part>.dart` (the TypeScript package) with a conditional
import on `dart.library.js_interop`. The new call `initWeb` loads the TypeScript package (on the native platforms it
does nothing); `tool/web_assets.sh` copies `dist/*.js` and `zmidi.wasm` into `lib/js/` (not in git). On the web, times
and tick counts go to 2^53 - 1, and `NetAddress` uses an address type of the package because the web has no `dart:io`.
The gates run the tests in Chrome with dart2js and dart2wasm.

## Context

Users of MIDI 2.0 in C, C++, TypeScript, Dart and Python cannot use the Rust crates now. A search of
2026-10-22 found no npm library with MIDI-CI, no pip library with UMP and MIDI-CI, and only one new
Dart package with UMP; Web MIDI has no UMP. C and C++ have libraries (AM_MIDI2, ni-midi2, midi2
C99, JUCE), but none has CI, PE, Network, BLE and USB descriptors in one, tested against the
specifications.

Spikes in the scratchpad (2026-10-22) showed:
- `zmidi-io` `BytesToUmp` through a C ABI works from C (host and Cortex-M4: 4084 B flash, 164 B RAM),
  Python ctypes, Node (WASM, 6.6 KB), Dart `dart:ffi` and Swift.
- A MIDI-CI Initiator and Responder with one-chunk PE work through the rules above with no change
  to `zmidi-ci` or `zmidi-ci-pe`: Discovery, PE Capabilities, Get, ResourceList and 404 between two
  devices in a C test (ASan, UBSan). Cortex-M4: 23874 B flash; WASM 43730 B.
- Corrosion v0.6.1 builds the library for the host and for `thumbv7em-none-eabihf`.
- A specdev project in `bindings/` does not change the check of the root `rust-workspace`.
- `specdev-analyzer report tests` lists a Rust test that runs a C test.

## Consequences

- The root `Cargo.toml` and `spec.toml` get the member `crates/zmidi-ffi`.
- `scripts/ffi-check.sh` runs the C tests, the CMake and Corrosion build for the host and for
  thumbv7em, and the check and tests of each `bindings/<lang>` project. The root gate script does
  not reach the binding projects. CI runs `ffi-check.sh` after the gates.
- The profiles `ts-library` and `dart-package` must be written with `/spec-create-profile`. Python
  waits for the Python support of specdev.
- Each const generic of a Rust type gets one fixed value in the C ABI (for example `CiDevice<4, 4,
  4>`). A different value needs a rebuild of `zmidi-ffi`.
- A size change of a Rust type can need a larger slot. That changes the ABI, so it changes the
  version of the C library.
- The FFI adds flash: each `extern "C"` function is a root for the linker. `scripts/ffi-check.sh` prints
  the flash and RAM of a bare-metal C link for each part; C jobs in `scripts/size-check.py` and
  `docs/sizes.md` are OPT-023. The packaging builds use the Cargo profile `ffi` (opt-level "s", LTO,
  one codegen unit).

## Alternatives

- An `ffi` module in each crate: rejected. It puts `unsafe` in every member, and gives several
  headers and several size policies.
- Callbacks (function pointer and `void *ctx`): rejected for the core ABI. They are difficult in
  WASM, Dart and Python.
- UniFFI or wasm-bindgen as the main binding: rejected. They need `std` and `alloc` and give a
  second API to test. A binding can still use them on top of the C ABI.
- Binding packages outside specdev: rejected. specdev can check TypeScript and Dart projects, and
  soon Python.
- Python before TypeScript: rejected for now. specdev has no Python support yet. (2026-10-22: specdev 0.4.0
  has Python support; the TypeScript and Dart profiles are not done yet.)
- Python with ctypes over the C ABI (the first plan): replaced by PyO3 (addendum above). ctypes needs
  hand-copied struct layouts and gives a C-shaped API in Python.

## Verification

- `cargo test -p zmidi-ffi` runs every C test; requirements of `zmidi-ffi` name these tests in
  `verified_by`.
- `cbindgen --verify` in CI: the header in the repository is current.
- `scripts/ffi-check.sh` in CI: host CMake + CTest, thumbv7em link with Corrosion, binding checks
  and tests.
- Each binding test checks the exported sizes of rule 6.
