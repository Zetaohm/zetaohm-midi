# DEC-003 — External USB, BLE and UART stacks; implement only MIDI-specific parts

**Status:** accepted

The library implements only the parts of each transport that MIDI
specifications define. It uses external crates for the general stacks and
contains no chip-specific code.

Implemented here:
- USB MIDI 2.0 device class (UMP endpoints, Group Terminal Blocks), on the
  `embassy-usb` builder. (Replaced by DEC-014 on 2026-10-17: USB-MIDI goes in
  the sans-IO crate `zmidi-usb`; `embassy-usb` and `usb-device` adapters are
  separate crates.)
- BLE-MIDI GATT service and packet codec (header and timestamps). (Replaced by
  DEC-016 on 2026-10-18: BLE-MIDI goes in the sans-IO crate `zmidi-ble`; the
  `trouble-host` adapter is a separate crate.)
- UART MIDI 1.0 byte stream codec (running status, real-time bytes inside
  other messages).
- UMP to MIDI 1.0 byte stream translation and the reverse.

External:
- USB device stack and the USB MIDI 1.0 class: `embassy-usb`
  (driver trait `embassy-usb-driver`).
- BLE host (GATT, advertising, pairing): `trouble-host` on `bt-hci`
  controllers.
- UART drivers: `embedded-io-async` traits.

Chip support (STM32, ESP32, nRF) comes from the HAL crates that implement
these traits. Example firmware for STM32WB55 and ESP32-S3 lives in
`examples/`, outside the Cargo workspace, and is not a specdev member.

## Context

Zetaohm hardware needs USB, UART and BLE on STM32, ESP32 and nRF. General
USB and BLE stacks are large and are maintained elsewhere. `embassy-usb` has
a USB MIDI 1.0 class and no USB MIDI 2.0 class.

## Consequences

- `zmidi-io` depends on `embassy-usb`, `trouble-host` and `embedded-io-async`,
  each behind a feature.
- ESP32 USB MIDI needs a part with USB OTG (ESP32-S2, S3 or P4). STM32 BLE
  needs an STM32WB part or an external controller over UART HCI.
- A change in an external stack API can need an adapter change in `zmidi-io`.

## Alternatives

- Own BLE or USB stack: rejected. Large, outside the MIDI specifications, and
  already available.
- Chip-specific drivers in the library: rejected. They tie the library to one
  vendor.
- `usb-device` instead of `embassy-usb`: rejected. It is synchronous, and
  `trouble-host` and the HALs follow the embassy model.

## Verification

CI builds the example firmware for STM32WB55 and ESP32-S3. `zmidi-io` has no
dependency on a HAL crate (`embassy-stm32`, `esp-hal`, `embassy-nrf`).
