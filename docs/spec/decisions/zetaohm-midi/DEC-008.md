# DEC-008 — MIDI-CI Profiles (M2-101 messages, M2-102 common rules) stay in zmidi-ci

**Status:** accepted

`zmidi-ci` implements MIDI-CI Profile Configuration as one of its modules: the
Profile messages of M2-101-UM (Universal SysEx Sub-ID#2 0x20 to 0x29 and
0x2F) and the common rules of M2-102-U (Profile ID, Profile addresses for a
Channel, Group, Function Block or several Channels, Manager and Member
Channels, Profile Details Inquiry). There is no separate Profiles crate.

A specification of one particular Profile (for example a Profile for one
instrument type) may become its own crate when a product implements it; that
crate depends on `zmidi-ci`.

## Context

Question: should Profiles be a separate crate? M2-102 section 2.4 restates the M2-101
Profile messages and adds rules for their use, so the rules and the messages
are closely coupled. Profiles need no JSON, compression or large buffers, and
M2-102 is short (30 pages).

## Consequences

- M2-102 catalogue rows that the library implements have the owner `zmidi-ci`.
- Profile state and messages use fixed buffers; DEC-002 applies with no
  exception.
- Rule for later splits: a separate crate is justified when a document adds a
  layer with its own dependencies or memory model (as Property Exchange does,
  DEC-006, DEC-007), not for every document.

## Alternatives

- A separate `zmidi-ci-profiles` crate: rejected. It would split code that
  depends closely on the M2-101 messages and add a specdev member, with no
  dependency or memory reason.
